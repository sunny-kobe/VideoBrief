## 全链检查范围与候选

| 环节 | 检查证据 | 下一步候选与约束 |
| --- | --- | --- |
| 来源发现、导入和处理 | 来源队列、失败原因、内容哈希、处理耗时 | 检查重复处理及错误分类；不把找不到资料当作事实不存在 |
| 研究和策划 | AI 调用、输入指纹、投影大小、草稿失效规则 | 测量重复上下文与缓存命中；不能省略事实确认 |
| 候选选片 | 候选窗口、素材清单、逐幕证据 | 检查重复素材探测与抽帧；保留窗口完整性、水印及可读性要求 |
| 配音 | preflight attempts、失败原因、缓存键 | 区分参数错误、窗口不足与供应商故障；避免确定性错误反复请求 |
| 渲染 | 场景命中率、耗时分组、失败恢复 | 继续验证局部修改缓存；不改变已确认窗口或循环补时 |
| 技术、语义与浏览器验收 | 校验次数、抽帧耗时、播放证据 | 降低重复计算；保留当前视频完整字节校验和一倍速完整播放 |
| 打包 | 大文件读取、重复复制、收据哈希 | 检查内存峰值与多版本校验；不复用失效验收或封面 |
| 全程测量 | 生产报告、有效样本数、计时覆盖 | 优先补齐可从已有事件推导的数据；日历跨度不算主动工时 |

默认入口：

```bash
node scripts/report-production-baseline.mjs
npm run project:production-report -- --brief=content/projects/<project-id>/project.json --format=summary
```

每轮记录触发证据、修改范围、验证结果、收益局限和下一步；没有新输入或未解决风险时不重复跑昂贵验证。外部工具与 Astra 剪辑流程没有同条件 A/B，不能声称端到端优于它们。

## 2026-09-10：大视频验收的内存峰值

发现：语义审查、浏览器验收的前后校验、打包主版本和 rendition 校验共 5 个调用点通过 `readFileSync` 将整段 MP4 载入内存。打包收据已经流式计算，不需要改动。

实现：`scripts/lib/hash-media-file.mjs` 使用 1 MiB 缓冲分块计算完整 SHA-256；替换上述 5 个调用点。不以路径、文件大小或修改时间缓存哈希；每个原校验位置仍读取当前全部字节。文件读取失败继续抛错，文件描述符在 finally 中关闭。

真实验证：读取已有 81,140,046 字节 MP4，四个独立进程按旧、新、新、旧顺序执行。四次哈希一致；旧实现峰值 RSS 为 125,504/125,744 KiB，新实现为 47,200/47,056 KiB。旧耗时 42.37/31.85 ms，新耗时 29.43/29.58 ms。仅证明该文件哈希过程的内存改善，不能外推整片耗时或所有硬件。原始证据保存在本地 `output/efficiency-media-hash-20260910.json`。

验证：315 项测试通过，`npm run lint` 通过；覆盖空文件、整块、部分尾块、保留大小和时间戳的内容替换、缺失文件。未修改或重新批准任何成片；未执行正式渲染、浏览器审片或打包。

保留的约束：`tests/frame-extraction.test.ts` 要求输入后定位以避免关键帧伪影。本轮不改变 seek 顺序；未来必须有逐帧一致性证据才考虑此项。

下一轮优先检查配音预检失败分类和重试路径，以及审片包生成是否正确验证已存在帧的版本。先复现问题再修改，不能仅因重复调用看起来昂贵就跳过校验。
