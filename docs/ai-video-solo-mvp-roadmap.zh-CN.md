# AI 视频消费工具个人项目 / 一人公司 MVP 落地方案

> 归档说明（2026-07-07）：本文是旧方向文档，已不再作为当前项目主线。当前最高优先级已经切换为 `海外 AI 信息再制生产台`，详见 `docs/overseas-ai-content-remix-roadmap.zh-CN.md` 和 `docs/ai-video-solo-founder-progress.zh-CN.md`。除非明确回看历史方案，不要继续按本文的 `英文公开视频 -> 中文研究笔记`、`MVP Pro Web/PWA`、登录、付费和 SaaS 路线推进。

> 基于 `ai-video-consumption-tool-roadmap.zh-CN.md` 的个人项目改写版。  
> 目标：不站在公司资源角度，而是站在一个人、副业、一人公司的角度，用最小 MVP 快速验证 Kim 所说的最终方向。

## 1. 核心结论

个人项目版不要一开始做“完整 AI 视频消费平台”，而要先做一个 **面向高价值人群的 AI 视频研究笔记工具**。

最小切口建议：

**帮中文/繁中用户快速理解英文 YouTube 商业、金融、科技视频，并自动生成中文研究笔记。**

这个切口和 Kim 的方向是一致的：

- 不是做 UGC 平台。
- 不是做短视频娱乐 App。
- 不是做普通翻译工具。
- 是把视频变成结构化信息、知识和可复用笔记。
- 先验证高价值用户是否愿意为“跨语言视频理解 + 节省时间”付费。

但执行方式要降维：

| 公司版 | 个人项目版 |
|---|---|
| 香港 + 日本双市场 | 先做中文/繁中高价值用户，香港/海外华人为主 |
| App + AI 底层基座 | 先做 Web/PWA + 少量自动化 |
| 多角色团队 | 一个产品/技术/增长全包 |
| 1000 付费用户 | 先验证 10 个付费用户，再到 50、100、300 |
| AI Agent 平台化 | 先把一个视频处理成高质量研究笔记 |
| 推荐/搜索/内容偏好 | 暂时不做推荐，先做用户主动输入视频 |

一句话：

**先做一个完成度足够高、能让用户自助体验并愿意付费的小产品，再逐步长成 Kim 说的 AI 视频消费工具。**

上一版“人工增强 MVP”适合验证需求，但用户感知会偏服务外包，不像一个真正的 AI 产品。现在有 Codex 这类 AI Coding 工具，个人项目的最低可接受版本应该上调：**第一版就要是可登录、可提交、可生成、可追问、可保存、可付费的 Web/PWA 产品。**

## 2. 个人版产品定位

### 2.1 推荐定位

产品可以暂定为：

**VideoBrief：把英文视频变成中文研究笔记。**

用户输入一个 YouTube 视频链接或粘贴 transcript，系统输出：

- 3 行核心结论。
- 分章节摘要。
- 关键观点和时间戳。
- 重要术语解释。
- 可追问的 AI 问答。
- 可复制到 Notion / 飞书 / Obsidian / 微信的 Markdown 笔记。

### 2.2 首批目标用户

个人版第一批用户不建议一开始做日本市场，因为语言、渠道、客服、支付、文案都会增加复杂度。

建议先做：

1. 香港/海外华人金融从业者。
2. Web3 / FinTech / 跨境创业者。
3. 需要看英文视频学习的中文职场人。
4. 想快速理解海外商业、AI、科技视频的人。

这些人有几个共同点：

- 他们经常接触英文内容。
- 他们时间贵。
- 他们愿意为效率工具付费。
- 你用中文就能做访谈、写文案、获客和客服。

### 2.3 第一阶段不要做什么

个人项目最怕一上来做大。

第一阶段不要做：

- 原生 iOS / Android App。
- 短视频 feed。
- 创作者生态。
- 自动推荐流。
- 自研大模型。
- 多国家本地化。
- 多人协作版。
- 浏览器插件。
- 复杂二创功能。

第一阶段只做一件事：

**用户给一个视频，产品给一份值得付费的中文研究笔记。**

## 3. 升级后的最小 MVP 定义

### 3.1 新判断：MVP 不能简陋，但必须收敛

这个项目的 MVP 应该是 **“窄而完整”**，不是“粗糙而简单”。

它可以只支持一个场景：英文 YouTube 视频 -> 中文研究笔记。  
但这个场景里的体验必须完整：

- 用户能自己注册登录。
- 用户能提交视频链接。
- 用户能看到漂亮、结构化、可复制的结果页。
- 用户能围绕视频追问。
- 用户能保存历史。
- 用户知道免费额度和付费价值。
- 用户愿意把结果截图或链接发给朋友。

所以 MVP 的定义要从“人工增强版”升级为：

**一个可上线、可演示、可自助使用、可收费的 AI 视频研究笔记 Web/PWA。**

### 3.1.1 为什么这里不能太简陋

这个产品卖的是“效率感”和“智能感”。如果第一版还像表单代处理，用户会把它理解成外包服务，而不是一个值得持续使用的 AI 工具。

现在有 Codex、Cursor、Claude Code 这类 AI Coding 工具，一个人做出完整 Web MVP 的成本已经下降很多，所以 MVP 的标准应该从“能不能跑”提高到“用户愿不愿意留下来用”。

这里要避免两个极端：

| 极端 | 问题 |
|---|---|
| 太简陋 | 用户看不出产品价值，不愿意注册、分享、付费 |
| 太庞大 | 一个人做不完，迟迟无法上线验证 |

正确做法是：

**场景要窄，体验要完整。**

也就是只做英文视频到中文研究笔记，但这条路径必须像一个成熟产品：登录、生成、结果页、追问、历史、额度、付费都要有。

### 3.2 推荐做法：直接做 MVP Pro，10-21 天

MVP Pro 不是大而全，而是把第一条核心链路做得像产品。

第一版只做 7 个页面：

1. **Landing Page**
   - 讲清楚产品价值。
   - 展示一份真实样例。
   - 提供“免费试 1 条视频”的入口。
2. **登录页**
   - 邮箱 magic link 或 Google 登录。
3. **Dashboard**
   - 显示历史视频、剩余额度、最近生成的笔记。
4. **新建分析页**
   - 输入 YouTube URL。
   - 粘贴 transcript fallback。
   - 选择输出模板：商业/金融/AI/课程学习。
5. **生成中页面**
   - 展示步骤进度：读取信息、清洗 transcript、生成摘要、生成章节、准备问答。
   - 不要让用户面对空白 loading。
6. **视频研究笔记页**
   - 这是核心产品体验。
   - 必须做得漂亮、清晰、可截图、可复制。
7. **付费页**
   - 免费额度用完后自然引导。
   - 可以先用 Stripe Payment Link / Checkout。

第一版必须有 8 个核心功能：

1. 账号登录。
2. 视频链接 + transcript 输入。
3. AI 生成结构化研究笔记。
4. 时间戳/章节结构。
5. 基于视频内容的追问。
6. 历史记录。
7. Markdown 复制。
8. 免费额度 + 付费入口。

### 3.3 最小但惊艳的结果页

用户愿不愿意用，70% 取决于结果页。

结果页建议布局：

```text
顶部：视频标题、来源、时长、语言、处理状态

左侧主栏：
  - 一句话结论
  - 3 行核心摘要
  - 分章节笔记
  - 关键观点
  - 术语解释
  - 行动清单
  - 原视频局限

右侧辅助栏：
  - AI Ask 输入框
  - 关键时间点
  - 复制 Markdown
  - 导出
  - 反馈按钮
```

结果页要给用户一种感觉：

**“我不用看完整视频，也已经抓住了这条视频的价值。”**

第一版输出结构：

```markdown
# {{视频标题}} - 中文研究笔记

## 一句话结论

## 3 行核心摘要

## 这条视频适合谁看

## 分章节笔记

| 时间 | 主题 | 重点 |
|---|---|---|

## 关键观点

## 重要概念解释

## 可以直接执行的行动清单

## 值得继续追问的问题

## 原视频局限

## 免责声明
```

### 3.4 可以保留人工，但只作为质检和增长

人工增强不再是产品形态，而是后台运营手段：

- 前 20 个用户的结果，你可以人工抽查。
- 对付费用户的前 3 条视频，你可以手动优化输出。
- 公开样例可以人工润色，保证传播效果。
- 用户反馈可以人工回访。

也就是说：

**产品看起来必须是自助工具，质量提升可以靠你在背后人工兜底。**

### 3.5 MVP Pro 不做什么

为了 10-21 天能上线，仍然要砍掉很多东西：

- 不做原生 App，只做响应式 Web/PWA。
- 不做 feed。
- 不做内容推荐。
- 不做多视频网站。
- 不做多人协作。
- 不做浏览器插件。
- 不做复杂知识库。
- 不做自动抓取全网热门视频。
- 不做二创视频生成。
- 不做实时字幕。

### 3.6 MVP Pro 验收标准

上线后 30 天内看这些指标：

- 100 个注册用户。
- 50 个用户完成视频分析。
- 20 个用户完成 2 次以上分析。
- 10 个付费用户。
- 至少 3 个用户主动分享结果。
- 至少 3 个用户提出愿意付费的明确理由。
- 单条视频处理成本和毛利可计算。

如果达到这些，说明项目值得继续。

## 4. 推荐技术栈

个人项目原则：少造轮子，少维护服务器，少处理脏活。

### 4.1 推荐栈

| 模块 | 推荐 |
|---|---|
| 前端/后端 | Next.js App Router |
| 部署 | Vercel |
| 登录和数据库 | Supabase Auth + Postgres |
| 权限 | Supabase Row Level Security |
| AI 生成 | OpenAI Responses API 或其他 LLM API |
| 音频转写 | 优先 transcript；必要时再用 OpenAI Speech to Text |
| 支付 | Stripe Checkout / Billing |
| 数据分析 | PostHog 或 Plausible |
| 邮件 | Resend / Loops |
| 文档导出 | Markdown 先行，后续再做 Notion/飞书 |

为什么这样选：

- Next.js + Vercel 适合一个人快速上线。
- Supabase 同时解决 Auth、DB、Storage、RLS，减少后端维护。
- Stripe Checkout 可以用托管支付页，少写支付代码。
- OpenAI Responses API 适合文本生成、结构化输出和后续 Agent 化。
- 先用 transcript，能明显降低成本和复杂度。

参考：

- [Next.js App Router](https://nextjs.org/docs/app)
- [Vercel Next.js deployment](https://vercel.com/docs/concepts/next.js/overview)
- [Supabase Auth](https://supabase.com/docs/guides/auth/)
- [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- [OpenAI Responses API](https://platform.openai.com/docs/api-reference/responses/create?api-mode=responses)
- [OpenAI Speech to Text](https://platform.openai.com/docs/guides/speech-to-text?lang=javascript)
- [Stripe Checkout](https://docs.stripe.com/payments/checkout)
- [Stripe Billing](https://docs.stripe.com/billing)

### 4.3 最小处理流程

```text
用户提交 YouTube URL
  -> 系统尝试获取公开元数据
  -> 用户粘贴 transcript 或系统使用合规可用 transcript
  -> transcript 清洗和分段
  -> LLM 生成结构化研究笔记
  -> 保存 Markdown
  -> 用户阅读、复制、追问
  -> 扣除 credit 或检查订阅权益
```

### 4.4 合规边界

个人项目更要保守，不要踩平台规则。

建议：

- 不下载、缓存或分发 YouTube 音视频内容。
- 不做绕过平台限制的解析器。
- 第一版允许用户粘贴 transcript，这是最稳的 fallback。
- 只保存用户生成的笔记、摘要和用户主动提供的文本。
- 对 YouTube API、字幕、缓存和用户数据做单独合规检查。
- 输出内容要附“基于用户提供/公开视频文本生成，不替代原视频，不构成金融建议”。

YouTube API Developer Policies 明确限制未经批准下载、导入、备份、缓存或存储 YouTube audiovisual content，所以个人项目第一版更适合走 transcript-first 和用户主动输入路线。

参考：

- [YouTube API Services Developer Policies](https://developers.google.com/youtube/terms/developer-policies)
- [YouTube API Policies Guide](https://developers.google.com/youtube/terms/developer-policies-guide)

## 5. 一人公司实施路线图

### 阶段 A：高质量样例和定位，2 天

目标：先做出“用户一看就懂价值”的样例，而不是只做概念页。

行动：

1. 选 3 条英文视频：
   - 1 条 AI/科技访谈。
   - 1 条金融/商业分析。
   - 1 条课程/学习型视频。
2. 用目标输出模板做 3 篇高质量中文研究笔记。
3. 人工润色样例，确保它们能被截图传播。
4. 写一句话定位：
   - “把 60 分钟英文视频，变成 5 分钟中文研究笔记。”
5. 写 3 个使用场景：
   - 没时间看完整英文访谈。
   - 英语能看但理解成本太高。
   - 想把视频变成可收藏、可分享、可追问的笔记。
6. 找 10 个目标用户看样例，不问抽象需求，只问：
   - 这份笔记有没有帮你省时间？
   - 你希望它再补什么？
   - 如果能自己提交视频生成，你会不会用？
   - 你愿意为每月 20 条视频付多少钱？

通过标准：

- 至少 5 人认可样例有用。
- 至少 3 人愿意试用产品。
- 至少 1 人愿意付费或愿意等上线。

### 阶段 B：MVP Pro 开发，10-21 天

目标：做出用户可自助体验的产品，而不是人工服务。

功能切片：

1. **第 1 刀：产品壳**
   - Landing page。
   - 登录。
   - Dashboard。
   - 新建分析页。
   - 结果页静态样例。
2. **第 2 刀：AI 生成链路**
   - 提交 URL 和 transcript。
   - transcript 清洗。
   - 生成结构化 Markdown。
   - 保存 note。
   - 生成失败重试。
3. **第 3 刀：结果页体验**
   - TLDR。
   - 章节。
   - 关键观点。
   - 时间戳。
   - 术语解释。
   - 复制 Markdown。
   - 反馈按钮。
4. **第 4 刀：视频问答**
   - 基于 transcript 追问。
   - 回答附引用片段或时间范围。
   - 不确定时提示无法从视频确认。
5. **第 5 刀：付费和额度**
   - 免费 1-3 条。
   - credits 或订阅。
   - Stripe Payment Link / Checkout。
   - 用量记录。

通过标准：

- 新用户 3 分钟内能完成第一条视频分析。
- 结果页能被截图分享。
- 处理失败有明确 fallback。
- 用户可以复制 Markdown 到 Notion/飞书/Obsidian。
- 每次生成的成本、耗时、失败原因都能记录。

### 阶段 C：封闭 Beta，7 天

目标：让 20-50 个目标用户真实使用，而不是只看 demo。

行动：

1. 邀请 20-50 个目标用户。
2. 每人给 3 条免费额度。
3. 对前 20 条生成结果做人工质检。
4. 每天收集反馈并只改最高频问题。
5. 每天发布 1 条公开样例。
6. 对强需求用户开放早鸟价。

通过标准：

- 至少 20 人完成第一次分析。
- 至少 8 人完成第二次分析。
- 至少 3 人付费。
- 至少 2 人主动分享结果。

### 阶段 D：公开 Beta 和收费，3-6 周

目标：验证它是不是副业产品，而不是一次性 demo。

行动：

1. 开放注册。
2. 上线免费额度和付费入口。
3. 每周发布 3-5 篇公开样例：
   - “这条英文 AI 访谈讲了什么？”
   - “60 分钟金融访谈，5 分钟看懂。”
   - “海外科技趋势视频中文研究笔记。”
4. 在 LinkedIn、X/Twitter、Telegram、微信群、Web3/FinTech 社群发。
5. 每周访谈 5 个用户。
6. 每周只改 3 个最影响留存和付费的问题。

通过标准：

- 100-300 注册用户。
- 50 个用户完成视频处理。
- 20 个用户完成第二次处理。
- 10 个付费用户。
- 至少一个稳定获客渠道。

### 阶段 E：一人公司雏形，2-3 个月

目标：从个人工具变成小型 SaaS。

新增能力：

- 模板库：金融、商业、AI、科技、课程学习。
- 批量处理。
- 长视频异步任务。
- 更稳定的 transcript/ASR fallback。
- 用户反馈驱动的质量评估。
- 简单知识库。
- 多人/小团队付费意向试探。

扩展路线：

1. 先中文/繁中用户。
2. 再英文输出。
3. 再日文市场。
4. 最后才考虑多市场、多语言、多渠道。

## 6. 30 天执行排期

| 时间 | 目标 | 具体产出 |
|---|---|---|
| Day 1 | 做样例 | 选 3 条英文视频，生成 3 篇高质量中文研究笔记 |
| Day 2 | 定位和页面原型 | 一句话定位、目标用户、landing page 文案、结果页线框 |
| Day 3-4 | 产品壳 | Next.js 项目、首页、登录、Dashboard、新建分析页 |
| Day 5-6 | 数据和权限 | Supabase 表、RLS、用户历史记录、credits 结构 |
| Day 7-9 | AI 生成链路 | transcript 输入、清洗、结构化 Markdown 生成、保存 note |
| Day 10-11 | 结果页体验 | TLDR、章节、关键观点、术语、行动清单、复制 Markdown |
| Day 12-13 | 视频问答 | 基于 transcript 追问、引用片段、不确定提示 |
| Day 14 | 内测版本 | 用 10 条真实视频跑通端到端，修失败路径 |
| Day 15-16 | 付费和额度 | 免费额度、Stripe Payment Link / Checkout、用量记录 |
| Day 17-20 | 封闭 Beta | 邀请 20-50 人试用，每天修最高频问题 |

| Day 28-30 | 公开 Beta | 开放注册、收费测试、复盘注册/使用/付费漏斗 |

### 6.1 用 Codex 加速的执行方式

既然 token 充足，开发方式可以更激进一点：每个功能切片都让 Codex 先生成实现，再由你检查体验和业务判断。

建议每天固定三段：

1. **早上：定义当天要交付的用户可见功能。**
   - 不写“优化系统”这种模糊任务。
   - 写成“用户能提交 transcript 并看到研究笔记结果页”。
2. **白天：让 Codex 完成开发、测试、修 bug。**
   - 每个切片都要求有最小测试。
   - 每天都跑通一次端到端路径。
3. **晚上：用真实视频验收。**
   - 至少处理 3 条真实视频。
   - 看结果是否足够让用户截图分享。
   - 把不满意的地方转成第二天任务。

个人项目使用 AI Coding 工具时，不要追求“代码架构一开始完美”，要追求：

- 每天都有用户可感知的进展。
- 每 3 天有一个可演示版本。
- 每周能找真实用户试用。
- 每次试用都能带回一个明确改进点。

## 7. 第一版 Prompt 输出标准

每次视频处理必须输出稳定结构，不能让模型自由发挥。

推荐输出：

```markdown
# {{视频标题}} - 中文研究笔记

## 一句话总结

## 3 行核心结论

## 适合谁看

## 分章节摘要

| 时间 | 主题 | 摘要 |
|---|---|---|

## 关键观点

## 重要概念解释

## 可以直接执行的行动清单

## 值得继续追问的问题

## 原视频局限

## 免责声明

本笔记由 AI 基于用户提供的视频文本生成，可能存在遗漏或理解偏差。涉及投资、法律、医疗等内容时，请自行核验原视频和专业来源。
```

质量标准：

- 不能编造视频里没有的信息。
- 重要观点要能对应到 transcript 片段或时间段。
- 中文要像人写的研究笔记，不要像机器翻译。
- 对金融/商业内容不能给投资建议。
- 对不确定的信息要明确写“不确定”。

## 11. 风险和处理方式

### 11.1 平台合规风险

处理方式：

- 不下载视频。
- 不保存音视频。
- 不绕过平台限制。
- transcript-first。
- 用户可手动粘贴 transcript。
- 上线前补隐私政策、服务条款和版权说明。

### 11.2 输出质量风险

处理方式：

- 先做人工检查版。
- 每条输出加免责声明。
- 对不确定内容要求模型标注。
- 重要观点附 transcript 片段或时间段。

### 11.3 成本风险

处理方式：

- 优先处理文本 transcript，不优先做 ASR。
- 免费用户限制长度。
- 长视频异步处理。
- 生成结果缓存。
- 每条视频都记录模型成本。

### 11.4 个人精力风险

处理方式：

- 每周只做一个核心改进。
- 不同时做香港、日本、欧美。
- 不同时做 Web、App、插件。
- 不同时做 B2C 和 B2B。
- 先收钱，再扩功能。

## 14. 最终判断

个人项目版最现实的路径是：

**高质量样例 -> MVP Pro Web/PWA -> 封闭 Beta -> 公开收费 Beta -> 小型 SaaS -> 多语言 AI 视频消费工具。**

关键不是一开始做得多完整，而是尽快完成第一轮闭环：

**让一个用户自己提交一条视频，3 分钟内看到一份足够惊艳的中文研究笔记，并愿意再处理第二条。**
